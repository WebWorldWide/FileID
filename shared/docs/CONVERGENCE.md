# Converging macOS onto the shared Rust engine

Plan for moving the macOS app from the Swift engine (`platforms/apple/engine`) to the shared Rust engine (`platforms/windows/src/engine`), drafted 2026-11-08 from `main` @ `8939acd6` (IPC 1.25.0, catalog v33). Counts come from STATE.md; nothing here was measured for the plan itself. NEXT.md tracks progress against these stages.

## Findings that shape the plan

- **One engine process at a time.** Per-command routing between the Swift and Rust engines inside the app's `EngineClient` would put two SQLite writers on one catalog, run two startup recoveries, two journal sets and two HNSW snapshots, and load models twice. `EngineClient.terminateRunningEngine()` exists to prevent two live engines. "Subsystem by subsystem" therefore means the order in which subsystems become ready under a Rust host; the app switches the whole engine at spawn.
- **Dogfood switch.** Since Stage 0 `EngineClient.locateEngineBinary()` starts `Contents/MacOS/fileidd` only when `engine.backend` (or `FILEID_ENGINE_BACKEND`) is `rust`; before, it preferred `fileidd` whenever present. The integrity check requires the same team ID. The adapters build writes events on fd 2, as the Swift engine does (`IPCTransport.bootstrap`).
- **State-folder trap.** On macOS the Rust engine keeps state in `~/.local/share/FileID` (the CLI/TUI folder). Only the app-hosted build may resolve `~/Library/Application Support/FileID` (or the sandbox container) and `fileid.sqlite`; CLI and TUI state must never merge with the app's.
- **Adapter design.** A Swift dynamic library in the app with a hand-written C interface, called from one new reviewed Rust file; ONNX models run from Rust through the CoreML execution provider of the existing `ort` crate; MLX models (VLMs, CLIP image, RAM++) stay in Swift adapters. No new crates.

## 2. Apple ML inside the Rust engine

### Options

- **A. In-process Swift adapters behind a C interface (recommended).** New SwiftPM product `FileIDAppleKit` (`platforms/apple/adapters/`), shipped as a dynamic library in `FileID.app/Contents/Frameworks/` with the app's team ID. It exports `@_cdecl` functions declared in a hand-written `fileid_apple.h` (no bindgen/cbindgen). Rust gets one module `src/apple/ffi.rs`, compiled only with `cfg(all(target_os = "macos", feature = "apple-adapters"))`, holding the only `extern "C"` block, added to the egress gate's reviewed inventory. Safe wrappers implement the seams that already exist: `shell::{trash,tags,ocr,heic,video,thumbnail}`, `face_refresh::Backend`, `TakeFaceAnalyzer`, `timeline::{FrameModel, FrameDecoder}`, `media_recipes::MediaRuntime`, CLIP-image and RAM++ backends, and a new `ResidentModel` lease that the MLX VLM and today's `VlmServer` both implement. Build in `assemble_app.sh`: `swift build --product FileIDAppleKit`, then `cargo build --release --features apple-adapters` with an rpath to `Contents/Frameworks`; no `build.rs` (its `Command::new` would trip the gate) and no `cc`/`swift-rs` crates. C conventions: plain structs and pointer+length buffers; Swift allocates and Rust frees through `fileid_apple_free`; async work returns a handle and completes through a C callback into a tokio oneshot; `fileid_apple_cancel(handle)`; every call reports bytes resident so Rust's `resource_scheduler.rs` is the single memory authority. Teardown: `fileid_apple_shutdown()` then `libc::_exit(0)`, the same hard exit the Swift engine uses to avoid MLX's destructor crash.
  - Pros: matches the owner's 2026-10-11 decisions (Apple services in-process, no separate model engine); zero-copy pixel buffers; one sandbox identity (the Rust binary inherits the sandbox as the Swift engine does today); reuses the pinned MLX, mlx-swift-lm, swift-transformers code.
  - Cons: a Vision or MLX crash takes down the engine (the app respawns at 1/4/16 s; Vision per-call timeouts carry over); one new reviewed FFI file; two toolchains in one build.
- **B. Helper process** (the Swift engine as an ML server). Isolates crashes but duplicates memory and warmups, copies every image across a pipe, adds a `Process` call site and a second signed binary. Superseded by the owner on 2026-10-11. Keep only the existing isolated decode workers: the Rust binary re-execs itself (`--sample-video`, `--convert-video`, `--export-photo`) through the reviewed `native_process.rs` launcher, with adapters doing the AVFoundation work in the child.
- **C. ORT CoreML EP from Rust.** Enable the existing `ort` crate's `coreml` feature on macOS (a feature of a locked crate; DECISIONS note) and bundle the official MIT `libonnxruntime.dylib` ≥ 1.22 in `Contents/Frameworks`. Good for SFace, BGE, CLIP text and YuNet (small graphs; the Swift engine already caches compiled CoreML models by hash, format, ORT and macOS version). Bad for RAM++ and CLIP image (the CoreML EP took 57 of 1,417 RAM++ nodes, 2,991 ms/image; an MLProgram session took 5–12 min to build).
- **D. MLX through mlx-c from Rust.** A new dependency, and Rust would re-implement Qwen3-VL/Gemma/Mistral, chat templates, tokenizers, prefix and prompt caches, and the custom MLX graphs that already exist in Swift. Rejected.

| Concern | A | B | C | D |
|---|---|---|---|---|
| Signing, notarization | one extra signed dylib | extra signed executable | extra signed ORT dylib | new native library |
| App Store sandbox | inherits as today | needs inherit, second process | fine | fine |
| Memory | single copy, Rust-governed | duplicated | single | single |
| Performance | same as Swift today | pipe copies, startup | good for small ONNX, poor for RAM++/CLIP image | unknown |
| No-new-dependencies rule | OK | OK | feature flag plus an approved runtime | violates |
| Egress gate | one new reviewed FFI file | new `Process` site | no new transport | new FFI |
| Owner decisions so far | matches | superseded | compatible | not approved |

### Recommendation: A + C

Swift adapters for MLX (VLM generation, chat, selection checks, goal ranking, benchmarks, transcription; CLIP image; RAM++) and for the other Apple frameworks (Vision faces/OCR/classify/saliency/eyes/humans/registration; ImageIO, VideoToolbox and the HEIF decoder; AVFoundation frames and exports; Speech; PDFKit/textutil; Trash, Finder tags, bookmarks, FSEvents, IOPM). Rust ORT with the CoreML EP for SFace, BGE and CLIP text only after an A/B shows parity with the Swift ORT path (vectors within 1e-5, latency within 10%); otherwise those stay in the adapter. Adapters own session mechanics only: no catalog writes, job policy or ranking.

## 3. Order of migration

### How the app switches

Whole engine at spawn, one process at a time.

- **Dev dogfood (no digest change):** put the Rust binary at `Contents/MacOS/fileidd`; add a macOS mode to `ipc/sink.rs` that writes events on fd 2 and sends library stderr to the log. The Swift engine stays as `FileIDEngine`.
- **Shipping flag (one owner-approved `EngineClient.swift` refresh, Stage 0):** an `engine.backend` = `swift|rust` setting (Developer ID builds) plus an env override; it picks the binary and the event stream and restarts through the existing single-flight `start()`.
- **Gaps under the Rust host** answer with the existing `unsupported` / `ToolCapability.available=false` replies the app already handles. Users stay on Swift by default until Stage 10.
- **Engine identity in tests:** add an optional `engine` (`"swift"|"rust"`) field to `ready` `EngineInfo` (schema first, minor IPC bump); `conformance.py` keys `$engine` and `knownDivergences` on it and falls back to stream detection.

### Gates for every stage

- **Catalog round trip:** the cross-engine conformance cases plus a new per-stage case (Swift writes, Rust on Mac mutates and undoes, Swift reopens and verifies), and a read-only copy of the owner's real catalog opened under Rust with People/Library/Restructure reads diffed against Swift.
- **Hardware:** the owner's M1 Pro 16 GB, isolated copies, release builds, quiet machine. Rust within +10% wall time and +10% peak footprint of Swift unless a stage says otherwise (owner to confirm); identical outputs for deterministic stages; private eval scores not worse beyond noise.

### Stage 0 status (2026-11-10, `agent/converge-0`)

Landed and proved headlessly; notarization and the on-screen dogfood run need the owner (checklist in NEXT.md).

- **Rust side.** Cargo feature `apple-adapters` (macOS only; CLI and TUI never enable it) builds the engine the app hosts. `src/apple/ffi.rs` is the only `extern "C"` block (ABI 1: version, shutdown, free, IOPM sleep assertion, bookmark lease open/close), registered in the egress gate; `src/apple/mod.rs` wraps it in safe types (`SleepAssertion`, `BookmarkLease`) and `run_hosted()`: events move to fd 2 (fd 2 is duplicated for the sink, then pointed at `logs/engine-stderr.log`, as the Swift engine does), then `server::run`, then `fileid_apple_shutdown()` and `_exit`. ## 4. Retiring the Swift engine

Retire when Rust has been the default for a release (or several weeks of the owner's daily use) without rollback; every conformance case passes on Rust on Mac with no darwin divergences; a copy of the owner's real catalog has been opened, mutated and undone by Rust and reopened by the last Swift engine without loss of names, identities, corrections or Undo; every Stage 5–8 metric is within tolerance on the M1 Pro 16 GB, an 8 GB Mac and a newer M-series Mac; the private eval sets are no worse; notarized DMG and App Store sandbox acceptance pass with the privacy and egress gates green.

Then delete the Swift engine code not moved into `FileIDAppleKit`, its GRDB writer and migrations (Rust migrations and `shared/catalog/*.sql` become the only source; `check_catalog_schema.py` keeps checking it), the Swift conformance CI step, and the Swift journal writers once dual-write ends. What stays Swift: the SwiftUI app, `FileIDShared` DTOs, the read-only `ReadStore`, QuickLook thumbnails, the Spotlight indexer, and `FileIDAppleKit` (Vision, ImageIO/VideoToolbox/HEIF, AVFoundation, Speech, PDFKit/textutil, MLX sessions, Trash, Finder tags, bookmarks, FSEvents, IOPM).

## 5. Risks and owner decisions

Decided 2026-11-10 (see DECISIONS.md): 1 approved with no new network code per stage; 2 bundle ORT with the `coreml` feature; 3 test-only Trash root in test builds only; 4 ±10% time/memory, evals within 0.02, on the M1 Pro 16 GB; 5 Rust NDJSON canonical, Swift dual-writes for one release; 6 Swift ships beside Rust for one release; 7 stays rejected. The original questions:
1. Approve the reviewed FFI surface (`src/apple/ffi.rs`, `FileIDAppleKit` in the egress inventory) and the locked-file refreshes per stage listed in section 0.
2. ORT on macOS: bundle the official MIT `libonnxruntime.dylib` and enable `ort`'s `coreml` feature, or keep ORT inference in the Swift adapter.
3. A test-only Trash root for conformance, or keep that case `run:false`.
4. Tolerances for "no regression" (±10% time and memory, eval deltas) and the reference hardware.
5. The canonical journal format and how long to dual-write.
6. Whether the Swift engine ships beside Rust for one release after the flip.
7. The alternative topology (Swift host linking the Rust core as a static library for SQL subsystems) is not recommended: two writers in one process and interfaces in both directions.

Risks: notarization and library validation for the Rust binary, adapters dylib, ORT dylib and `mlx.metallib` (which MLX finds next to the executable); App Store sandbox behaviour of the Rust binary (bookmark resolution, container paths) is unproven until a signed TestFlight run; the Swift runtime in a Rust host (no `@main`, no run loop assumptions, Vision and AVFoundation on their own queues); in-process crash blast radius (rely on respawn and durable job resume); numeric drift between the CoreML EP and Swift ORT or MLX and ORT (keep the face processing id and `clip_model` id identical, or trigger the refresh paths deliberately); Rust keyword search latency; memory governance with two allocators under one scheduler (MLX cache caps and idle park must keep working); state migration (HNSW snapshots rebuild, journals import, benchmark results and sentinels map, all idempotent and one-way with dual-write); headless CI cannot prove any stage, so notarization, sandbox, on-screen and eval checks need the owner's Mac.
