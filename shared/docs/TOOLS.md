# File tools: supported exports and recovery

Video conversion accepts optional `videoAspectRatio` values `source`, `9:16`, `16:9`, `1:1`, and `4:5`. The workers use 1280/1920 long-edge presets to fit the entire displayed source into the requested canvas, padding unused space. They do not crop or track subjects. Generated media tests verify preserved audio and duration, source hashes, metadata removal, and Undo. The Linux/Windows adapter advertises video only when its vetted local FFmpeg/OpenH264 runtime is installed; otherwise it rejects video plans before mutation.

Tools use typed IPC requests; v1.4 adds the video recipe; v1.9 adds optional conventional photo enlargement. Preview resolves an exact catalog selection, fingerprints source bytes with SHA-256, reserves collision-safe output names, and stores an immutable operation plan. Execute uses that saved plan, checks sources and chapter snapshots again, stages each output, validates it, and publishes with a non-overwriting hard link. The original is never mutated. This requires an output filesystem that supports hard links; unsupported publication fails explicitly.

Capabilities describe the adapter actually running; they do not promise every format pair on every OS.

## History and Undo

Every output enters the catalog with an original/export relationship and its recipe. Completed receipts, output hashes, staging paths, and derived catalog IDs are journaled. History survives restart and engine changes, including undone exports and their recovery paths. Completed, failed, and undone plans require a fresh preview before another execution. Undo checks all remaining exports before moving them into `ExportRecovery/<operation-id>` beside the internal catalog; edited exports are left untouched. Recovery paths are shown to the user, so Undo does not permanently delete generated files. Moving an export across filesystems can fail on the Rust adapter; the original remains untouched and the operation journal remains available.

Interrupted exports become failed operations instead of replaying a possibly ambiguous write. Registered staging files are cleaned after a short parent-worker grace period. Cleanup requires an owned UUID filename, the recorded output directory, a regular file, and a writable unprotected location; it preserves unrelated files and aliases. A crash between filesystem publication and receipt acknowledgement can leave a prepared output for manual review. General batch restart/resume and a fully reconciled publication journal remain release gates.

The native macOS File Tools window is accessible from the existing toolbar. It supports catalog search, multi-selection, recipe/output-folder selection, exact preview, export, cancellation, persistent last-operation history, and Undo. Closing and reopening Tools retains its session, and closing the main window does not terminate an active engine. Recipe and source controls are disabled while a tool request is pending. Native WinUI and GTK File Tools dialogs route search, multi-selection, capability-driven recipe controls, folder picking, preview, export, history, Stop export, and Undo through the existing engine. They hide unavailable adapters and invalidate saved previews when inputs change. GTK unsubscribes its event task on dialog close; Windows detaches engine listeners. Linux and Windows engine/GUI builds and tests passed in scratch VMs; the Windows app also launched interactively. End-to-end clicking of the native File Tools stop control remains to be verified. The portable decoder isolation and full toolbox remain open.

Adlon and managed media-library originals are protected before any output is created, including alias and missing destination checks. Modification and interoperability tests use internal temporary directories only. The owner approved FFmpeg/OpenH264 as an optional portable runtime dependency; no new Rust crate, Swift package, or model weight was introduced.

## Native video export verification

Rights-clear generated portrait footage and a generated tone exercise actual child-worker probing/export, H.264/AAC, audio/video timing, orientation, metadata stripping, source hashes, derivative registration and Undo. Explicit MP4 MIME hints permit native validation while the owned output still has its .part staging name. AVURLAsset reference restrictions forbid external media references. The macOS and Rust subprocess modules are source-digest pinned after review. Rust rejects a saved video plan before output mutation when its vetted runtime is missing.

Apple documents these presets as H.264/AAC exports: https://developer.apple.com/documentation/avfoundation/avassetexportpreset1920x1080. The Apple worker uses the operating system framework. The portable runtime build recipes are `shared/scripts/build_ffmpeg_lgpl_linux.sh` and `shared/scripts/build_ffmpeg_lgpl_windows_x64.sh`; their development bundles include FFmpeg and OpenH264 sources, licenses, checksums, and build records. The Windows development build can stage a verified x64 runtime with `build-all.ps1 -MediaDir <absolute path>`; release staging remains blocked pending codec patent/distribution review. ARM64 runtime packages, full color/fidelity matrices, unusual audio offsets, HDR-preserving export, and resumable batches remain gates.

## Conventional enlargement verification

Omitted/false `allowUpscale` preserves existing small-image dimensions. True fills the requested long-edge bound while preserving aspect and orientation; it does not recover missing details or implement neural enhancement. The macOS worker accepts both the legacy four-argument invocation and the bounded five-argument flag. Shared recipe DTOs mirror the optional boolean in Swift/Rust/C#. Other tools reject true before execution. Tests verify input hashes, PNG/JPEG/TIFF output geometry, protected destinations, collision handling, derivative recipes, and recovery history. Actual saved Swift and Rust plans execute across engine changes, including enlargement and persistent Undo.

For isolated GTK QA on this Mac, stage both the app and engine under `/tmp`; loading the engine from the Desktop checkout stalled in dyld before its entry point. Copying the same built executable to internal scratch storage resolved startup without a client-code change. This is a development-host observation, not a Linux diagnosis.
